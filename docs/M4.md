# M4 — режим «что если»

В карточке сотрудника готово сравнение текущего расчёта со сценарием.
Все подстановки пересчитываются сразу, через тот же движок. Сценарий живёт
только в сессии интерфейса: загрузчики, начисления и закрытые снимки его не получают.

## Как проверить

Запустите `uv run streamlit run app/main.py`, откройте
http://127.0.0.1:8501. Если реестр пуст, загрузите условные образцы в «Загрузка».

1. Откройте «Сотрудники», выберите **T0008 / TP-T05**, нажмите «Что если».
   Без подстановок обе колонки совпадают. Постоянно показана пометка
   «Моделирование, не является обещанием выплаты».
2. Включите **«Исторический сценарий»** — у образцов вехи уже закрыты.
   Отметьте «Моделировать: Мотивационная веха 3». Выберите сдвиг от плана:
   при −50…−100 днях сумма промежуточной вехи остаётся на потолке, цена дня — 0.
   Изменение аванса может менять финал и проценты: это видно отдельно.
3. Для **T0010 / TP-T06** можно задать факт вехи 3 датой на 120 дней позже
   плана: сумма и цена дня равны нулю. Ползунок ограничен ±100 днями,
   календарь позволяет проверить более длинную просрочку.
4. Для **T0026 / TP-T14** подставьте NPV через полгода **4 900 000 000 ₽**:
   последняя часть получает статус «приостановлено», итог и ближайшая выплата
   пересчитываются. Верните исходное значение кнопкой «Сбросить сценарий».
5. Для **T0018 / TP-T10b** в историческом режиме измените долю БС с 60% на 95%:
   множитель меняется с 0,94 на 1. Для МП доступны квартальные KPI 0…150%.
6. Для **T0028 / TP-T15** измените дату ухода с 31.03.2026 на 30.04.2026:
   остаток меняется. В том же блоке можно изменить БГБ и загрузку отдельно
   по каждому периоду, сохраняя исходную историю остальных периодов.
7. Нажмите «Сбросить сценарий»: восстанавливаются исходные факты, поля и
   точный результат. Смена сотрудника/назначения или ревизии источников также
   очищает черновик. Сценарий не меняет журнал, реестр и файл закрытого квартала.

В обычном режиме закрытые факты и их NPV/БС фиксированы. Текущий NPV и доля БС
относятся к незакрытым событиям; для изменения условий прошлого явно включается
исторический режим. Контрольные NPV q1/q2 подставляются отдельно. Сценарная дата
означает и факт, и закрытие в 1С. При переносе дат остальные финансовые входы
не выбираются заново из другого квартала; KPI МП пересобирается по квартальной
истории. Ручное согласование исходного опережения и исходная дата вне сессии
не распространяются на перенесённое событие.

## Что показывается

- Две колонки: итог этапа, проценты, ближайшая выплата с датой, ПБ и коэффициенты.
- Таблица сумм и различий по вехам, финалу, частям, процентам и итогу, со статусами
  и датами выплат. Финал и его части не складываются повторно.
- Цена дня для незакрытых вех, в историческом режиме — и для закрытых.
  Сравнивается сумма конкретной вехи при выбранном факте и на день раньше.
  Если факт не задан, опора — индивидуальный срок, иначе общий план.
  Для промежуточной вехи в зоне просрочки ≥100 дней индикатор равен 0;
  реальный перенос с 100 на 99 дней пересчитывает бонус по обычной формуле.
  Потолок 150% относится к промежуточным вехам; у ключевой — К срока этапа.
- Явная дата отсчёта ближайшей выплаты, без зависимости от часов компьютера.
  По умолчанию используется конец выбранного квартала.
- Проблемы и статусы сценария. Итог включает только рассчитанные суммы;
  неизвестные, ожидающие и приостановленные суммы не выдаются за начисление.

## Проверки

**270 тестов прошли**, Ruff и проверка форматирования — без замечаний.
Пакетный CLI и сверка 27 эталонов: **0 расхождений**. Режим дополнительно
проверен в локальном браузере: выбор сотрудника, открытие моделирования,
исторический факт, выбор сдвига, сравнение итогов. Шаблон, эталоны и samples
не изменялись.

Автоматизированы свойства TEST_PLAN §4, контрольные T05/T06/T14/T10b/T15,
неизменность входного кейса, точное совпадение без изменений на всех 28 кейсах,
KPI по кварталам, изменение периода БГБ/загрузки, ограничения значений,
доступ сервисного слоя и сохранение ограничений ручных решений.

Проверяется SHA-256 физического файла SQLite до и после повторных сценариев,
неизменность ревизии, журнала, закрытого снимка и выгрузки. AppTest проходит
изменение NPV, даты/ползунка, БС, БГБ, KPI, сброс и переход к другому сотруднику;
отдельно проверяет хэш БД при действиях в интерфейсе.

В отдельном замере по **42 условным назначениям** на этом Mac полный вызов
сервиса с исходным/сценарным расчётом и ценами дня занял в среднем **0,011 с**,
максимум **0,021 с**. В тестах проверяется порог ≤1 с. Время передачи страницы
браузеру в этот замер не входит. Зависимости не добавлялись, сеть для работы
не нужна. Windows остаётся целевой платформой, запуск на ней пока не проверен.
