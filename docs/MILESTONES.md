# Хранилище вех: начальная загрузка и обновление файлом

Дополнение к комплекту `sov-bonus-kit`. Положить в `docs/MILESTONES.md`. Уточняет загрузчик вех этапа M2 (`DATA_FORMATS` §3, файл `milestones_1c.xlsx`). Что добавить в `CLAUDE.md` и `docs/DECISIONS.md` — в разделе 10.

Хранилище вех — таблицы `milestone` и `milestone_plan_version` с полным списком вех **всех** проектов, очередей и этапов, а не только тех, по которым уже есть калькулятор. Из хранилища берутся вехи для нового калькулятора (`docs/NEW_CALC.md`) и даты для расчёта.

Работа с хранилищем выглядит так:

1. Один раз загрузить начальную версию: полную выгрузку вех из 1С.
2. Дальше просто загружать свежую выгрузку. Система показывает, что изменилось: новые вехи, перенос плана, закрытие. После «Применить» даты обновляются, старые плановые даты остаются в истории.

Сейчас то же делают макросы и формулы калькулятора (приложение А). Правила ниже повторяют их поведение там, где оно правильное, и закрывают его слабые места.

---

## 1. Ограничения

Действуют все жёсткие правила `CLAUDE.md`. Дополнительно:

- Агент разрабатывает и тестирует загрузчик **только на условных выгрузках** из `samples/milestones/` (раздел 9).
- Начальную версию на реальной выгрузке загружает пользователь сам, в запущенном приложении. Реальный файл в git не кладётся, база реестра лежит в `data/`, а `data/` в `.gitignore`.
- Загрузчик ничего не пишет в исходный файл. Принимается `.xlsx`. На `.xls` и `.xlsm` загрузчик отвечает «сохраните выгрузку как .xlsx».
- Ничего не удаляется автоматически. Если веха пропала из выгрузки, это вопрос, а не удаление (п. 6.2).

## 2. Входной файл

### 2.1. Макеты

| Тип | Признак | Где шапка | Особенности |
| --- | --- | --- | --- |
| `MILESTONES_1C` | обязательные заголовки (п. 2.2) в одной строке | ищется в первых 10 строках. В выгрузке, которую берёт макрос, шапка во 2-й строке, данные с 3-й, колонки B–V | кодов проекта и вехи нет |
| `MILESTONES_1C_CODES` | то же плюс `Код проекта`, `Код вехи` | любая из первых 10 строк | макет `samples/milestones_1c.xlsx` |

Колонки ищутся **по заголовку**, а не по букве. Заголовки сравниваются после trim и схлопывания пробелов (в шаблоне есть `Отдел разработки продукта ` с пробелом на конце). Лист — первый, или `Лист для загрузки вех`, если он есть. Если подходящих листов несколько, пользователь выбирает лист в предпросмотре.

### 2.2. Колонки

| Колонка | Обязательна | Что делать |
| --- | --- | --- |
| `Статус` | да | п. 2.3 |
| `Наименование` | да | как есть. Для ключа нормализуется (п. 3) |
| `Ключевая` | да | `Да` / `Нет` без учёта регистра и пробелов. Другое значение — `MS_BAD_VALUE` |
| `Проект` | да | название из 1С. В код проекта переводится через `project_alias` (`RASST` §4.2), если нет колонки `Код проекта` |
| `Очередь/корпус/строение` | да | текст как есть (`queue_raw`). Пусто — веха проекта без очереди (п. 3.3). В очередь реестра переводится через `queue_alias` |
| `Этап` | да | `Четвертый этап`, `4`, `4 этап`, `4-й этап` → 4. Учитывать `ё/е` и неразрывные пробелы. Иное — `MS_BAD_VALUE` |
| `Плановый срок` | да | дата Excel или текст `ДД.ММ.ГГГГ` (также `ДД.ММ.ГГ`, разделители `/ - \`). Год из двух цифр: меньше 30 → 20xx, иначе 19xx. Несуществующая дата (`31.02.2026`) — ошибка `MS_BAD_DATE`, а не перенос на март, как в `DateSerial` |
| `Фактический срок` | нет | то же правило дат. Пусто — факта нет |
| `Дата закрытия в 1С` | нет | п. 4. Если колонки нет, см. там же |
| `Код проекта`, `Код вехи` | нет | если есть, это ключи (п. 3.1) |
| `Шаблон`, `Вид`, `Критерий закрытия`, `Заказчик`, `Исполнитель` | нет | хранить. В расчёте не используются |
| `Руководитель проекта`, колонки отделов (`Отдел Интерьеров` и др.) | нет | флаги `Да/Нет`, хранить в `extra_json`. В расчёте не используются. Если окажется, что по ним веха не участвует у подразделения, это новое правило, а не загрузчик (`docs/RULE_CHANGES.md`, уровень 3) |
| любые другие | нет | хранить в `extra_json` |

### 2.3. Статусы

| Значение 1С | `status` | Смысл |
| --- | --- | --- |
| `Назначена` | `assigned` | веха в плане |
| `Выполнена` | `done` | веха выполнена |
| любое другое | как есть | `MS_STATUS_UNKNOWN`, вопрос. Строка загружается, но статус не меняется, пока пользователь не решит, что значит это значение (`status_alias`, раздел 8) |

На практике встречались только `Назначена` и `Выполнена`. Если появится статус вида «Отменена», веха не удаляется и не выпадает из калькуляторов сама: нужно решение `milestone_inactive`.

## 3. Ключ вехи

### 3.1. С кодом

Если в файле есть `Код вехи`, ключ — он.

### 3.2. Без кода (реальная выгрузка сейчас)

Ключ натуральный: `(project_code, queue_raw, stage, name_norm)`.

- `name_norm` — наименование после trim, схлопывания пробелов, замены `ё` на `е`, без учёта регистра.
- `queue_raw` — после trim; пустая очередь — отдельное значение.

Связь натурального ключа и `milestone_code` хранится в таблице `milestone_key`. Код создаётся один раз при первой загрузке и дальше не меняется: `TP-07/1/4/0012`, где последние цифры — порядковый номер в этапе. В предпросмотре один раз показывается предупреждение `MS_NO_CODES`: «в выгрузке нет кодов вех, сопоставление по проекту, очереди, этапу и наименованию».

### 3.3. Особые случаи

- **Дубль ключа в файле.** Две строки с одинаковыми проектом, очередью, этапом и наименованием — `MS_DUPLICATE_KEY`, блокирует обе строки. Формула калькулятора в таком случае молча берёт первую строку (приложение А), система угадывать не должна.
- **Веха без очереди.** Строка проекта с пустой очередью — веха проекта (общая для очередей). В калькулятор очереди она попадает, только если её плановая дата не позже ключевой вехи этой очереди (`NEW_CALC` §4).
- **Вехи из двух частей.** Наименования, оканчивающиеся на `(часть 1)` и `(часть 2)`, — две разные вехи со своим весом. Макрос тоже вставляет обе. Проверка `MS_PART_PAIR`: есть только одна часть, или у части 2 дата раньше, чем у части 1. Это толкование, его подтверждает Группа СОВ (раздел 10).
- **Переименование.** Если в этапе одна веха пропала, а другая появилась, и у них совпадают плановая дата или `Шаблон`, это `MS_POSSIBLY_RENAMED`. Пользователь решает: переименование (`milestone_rename`, код сохраняется вместе с историей) или новая веха.
- **Перенос в другой этап.** Та же веха (по наименованию и очереди) пропала в этапе N и появилась в этапе M — `MS_POSSIBLY_MOVED`, вопрос.

## 4. Что хранится

Поля к таблицам `DATA_FORMATS` §4:

| Таблица | Добавить |
| --- | --- |
| `milestone` | `queue_raw`, `name_raw`, `template`, `kind` (Вид), `status_raw`, `criterion`, `extra_json`, `first_upload_id`, `last_seen_upload_id`, `is_active` |
| `milestone_plan_version` | `upload_id`. `valid_from` — дата выгрузки (п. 5) |
| `milestone_key` (новая) | `natural_key`, `milestone_code` |
| `milestone_raw_row` (новая) | `upload_id`, `row_no`, `raw_json` — строка файла как есть, со всеми колонками. Нужна для трассировки и для файла калькулятора на время параллельного расчёта (`NEW_CALC` §7) |

Изменения факта, статуса и признака «ключевая» пишутся в `audit_log` (было / стало, загрузка). Плановая дата меняется только новой версией в `milestone_plan_version`, старые версии не правятся.

**Дата закрытия в 1С.** Если такой колонки нет (реальная выгрузка сейчас), `closed_1c_date = null`, а статус `Выполнена` считается закрытием в 1С. Дата для квартала начисления в этом случае — фактическая дата, как в шаблоне (`CALC_RULES` И-8). Проверка `FACT_WITHOUT_1C_CLOSE` при этом не срабатывает на каждую веху. Вместо неё одно предупреждение на загрузку и проверка `MS_STATUS_FACT_MISMATCH` (раздел 7).

## 5. Начальная версия

Это тот же загрузчик в режиме «Начальная версия». В интерфейсе это переключатель на экране «Загрузка», в командной строке:

```
uv run python -m sov.loaders.milestones seed <файл.xlsx> --export-date ДД.ММ.ГГГГ
```

- Режим разрешён только для проектов, по которым в хранилище ещё нет вех. Для остальных проектов файла строки идут как обычное обновление.
- **Дата выгрузки** вводится в предпросмотре. По умолчанию это дата изменения файла. Она становится `valid_from` первой версии плановой даты, основание — «начальная загрузка, выгрузка 1С от ДД.ММ.ГГГГ».
- Предпросмотр начальной версии вместо «добавится / изменится» показывает сводку и проблемы:
  - сколько проектов, очередей, этапов и вех;
  - этапы без ключевой вехи и этапы с несколькими ключевыми;
  - несопоставленные проекты и очереди (через те же справочники, что и для расстановок);
  - строки с ошибками дат, этапов и статусов.
- Если 1С выгружает вехи только по проекту, загрузить несколько файлов одной пачкой. Они применяются как одна загрузка.
- После применения экран «Проекты» показывает дерево «проект → очередь → этап → вехи».

## 6. Обновление

### 6.1. Порядок

Общий порядок загрузки (ТЗ, раздел 5): распознать → проверить → сопоставить → предпросмотр → «Применить» с журналом → повторная загрузка ничего не меняет → откат до закрытия квартала.

### 6.2. Охват

- В обновлении участвуют только **проекты, которые есть в файле**. Вехи других проектов не трогаются.
- Если веха проекта из файла есть в хранилище, но её нет в файле, это `MS_MISSING_IN_FILE`. Это вопрос, сама веха не удаляется и не выключается.
- Переключатель «файл полный» (все проекты) дополнительно показывает проекты из хранилища, которых нет в файле. Это только информация.

### 6.3. Что меняется

| Изменение в файле | Что делает «Применить» | Проблема |
| --- | --- | --- |
| новая веха | добавить веху и версию 1 плановой даты | если у этапа уже есть калькулятор — `NEWCALC_SET_CHANGED` (`NEW_CALC` §4.3) |
| плановая дата изменилась | новая версия, `valid_from` = дата выгрузки, основание = файл | `MS_PLAN_MOVED` (информация, сдвиг в днях) |
| то же у ключевой вехи | то же | `MS_KEY_PLAN_MOVED`: меняются длительность этапа и ПБ. В предпросмотре — у скольких назначений и на сколько. Выплаченные авансы не пересчитываются (`CALC_RULES` §13, перенос вех) |
| появился факт | записать `fact_date`, статус | — |
| факт изменился | записать, старое значение — в журнал | `MS_FACT_CHANGED`. Если аванс по вехе уже в закрытом квартале — `MS_FACT_CHANGED_CLOSED`, блокирует: только корректировка в следующем квартале по решению |
| факт пропал или статус `Выполнена` → `Назначена` | **не применять** | `MS_FACT_REMOVED`, блокирует |
| признак «ключевая» изменился | **не применять** | `MS_KEY_CHANGED`, блокирует: меняется окончание этапа |
| `Шаблон`, `Вид`, `Критерий`, флаги отделов | записать | без проблемы, только счётчик в предпросмотре |

### 6.4. Индивидуальные сроки

В выгрузке вех их нет. Они приходят отдельным файлом (`individual_dates.csv`) или решением `individual_term` из расстановок (`RASST` §8). Перенос плановой даты индивидуальный срок не меняет. Если новый план стал позже индивидуального срока, это `MS_INDIVIDUAL_OUTDATED`: «индивидуальный срок раньше нового плана, действует ли он».

## 7. Проверки: коды проблем

Дополнение к `CALC_RULES` §12.2. Формат прежний, плюс `source_ref` (лист и строка файла) и `proposal`.

| Код | Блокирует | Что обнаружено |
| --- | --- | --- |
| `MS_BAD_DATE` | да, строку | дата не читается или не существует |
| `MS_BAD_VALUE` | да, строку | этап или признак «Ключевая» не распознан |
| `MS_NO_PLAN_DATE` | нет | у вехи нет плановой даты. Макрос такие вехи молча пропускает |
| `MS_DUPLICATE_KEY` | да, строки | две строки с одним ключом (п. 3.3) |
| `MS_PROJECT_UNMATCHED` | да, строки | проект или очередь не сопоставлены |
| `MS_NO_CODES` | нет | в файле нет кодов вех, сопоставление по натуральному ключу |
| `MS_STATUS_UNKNOWN` | да, статус | статус не из таблицы п. 2.3 |
| `MS_STATUS_FACT_MISMATCH` | нет | `Выполнена` без факта или факт при статусе `Назначена` |
| `MS_STAGE_NO_KEY` | нет | у этапа нет ключевой вехи. Если по этапу есть калькулятор — `FINAL_PLAN_MISSING` |
| `MS_STAGE_MULTI_KEY` | нет | в одной очереди и этапе несколько ключевых вех |
| `MS_PLAN_MOVED` | нет | перенос плановой даты |
| `MS_KEY_PLAN_MOVED` | нет | перенос плановой даты ключевой вехи |
| `MS_FACT_CHANGED` | нет | факт изменился |
| `MS_FACT_CHANGED_CLOSED` | да | факт изменился, аванс уже в закрытом квартале |
| `MS_FACT_REMOVED` | да | факт пропал или статус вернулся в `Назначена` |
| `MS_KEY_CHANGED` | да | изменился признак «ключевая» |
| `MS_MISSING_IN_FILE` | нет | веха проекта из файла отсутствует в файле |
| `MS_POSSIBLY_RENAMED`, `MS_POSSIBLY_MOVED` | да, пару строк | п. 3.3 |
| `MS_PART_PAIR` | нет | непарная часть или части в обратном порядке |
| `MS_INDIVIDUAL_OUTDATED` | нет | п. 6.4 |

## 8. Решения: `manual_decision`

| kind | Что значит | Пример `payload_json` |
| --- | --- | --- |
| `status_alias` | значение статуса 1С и его смысл | `{"raw":"Отменена","status":"inactive"}` |
| `milestone_inactive` | веха снята: не входит в новые калькуляторы, из существующих убирается только решением `calc_set_change` | `{"milestone_code":"TP-07/1/4/0012"}` |

## 9. Интерфейс и тесты

**Экран «Загрузка».** Для вех добавить:

- сводку по проектам: сколько вех добавится, перенесётся, закроется, пропало;
- фильтр «только ключевые»;
- колонку «сдвиг плана, дней».

**Экран «Проекты».** Нужны дерево вех и история плановой даты по каждой вехе (версия, дата, основание, файл).

**Тесты.** Генератор `tools/make_milestone_samples.py` собирает условные выгрузки в `samples/milestones/` по сценариям `tests/milestones/scenarios.json`.

- Вёрстка как у реальной выгрузки: строка 1 — заголовок или номера колонок, шапка во 2-й строке, данные с колонки B, даты текстом `ДД.ММ.ГГГГ`, этап словами, заголовок с пробелом на конце, колонки отделов.
- Файлы:
  - `ms_seed.xlsx` — начальная версия;
  - `ms_update1.xlsx` — переносы, новые вехи, закрытия;
  - `ms_update2.xlsx` — ошибки;
  - `ms_codes.xlsx` — макет с кодами.

| ID | Что проверяет |
| --- | --- |
| M01 | оба макета распознаются, шапка найдена во 2-й строке, колонки по заголовкам |
| M02 | этап словами и цифрой, `ё/е`, неразрывный пробел |
| M03 | даты: текст, число Excel, год из двух цифр, `31.02.2026` — ошибка |
| M04 | начальная версия: сводка, этапы без ключевой и с двумя ключевыми, `valid_from` = дата выгрузки |
| M05 | натуральный ключ: код стабилен между загрузками, дубль ключа блокирует |
| M06 | веха без очереди хранится как веха проекта |
| M07 | перенос плана: новая версия, старая цела. Ключевая веха — `MS_KEY_PLAN_MOVED` с числом назначений |
| M08 | появление и изменение факта. Изменение при закрытом квартале блокирует |
| M09 | пропал факт, вернулся статус, сменилась ключевая — не применяется |
| M10 | веха пропала из файла: вопрос, ничего не удалено. Проекты вне файла не тронуты |
| M11 | неизвестный статус, затем `status_alias` |
| M12 | переименование и перенос в другой этап |
| M13 | `(часть 1)` и `(часть 2)`: две вехи. Непарная часть — `MS_PART_PAIR` |
| M14 | повторная загрузка ничего не меняет, откат возвращает хранилище и версии |

**Готово, когда** все сценарии дают ожидаемые проблемы и изменения, повторная загрузка ничего не меняет, откат возвращает реестр. Кроме того, пользователь загрузил условную начальную версию и два обновления и на экране «Проекты» видит историю переносов.

## Приложение А. Как это работает сейчас

Проверено по коду макрокниг и по копиям калькуляторов.

- **«Загрузить вехи во все калькуляторы»** (книга КУПК) берёт выгрузку 1С (первый лист, данные с 3-й строки) и папку калькуляторов, без подпапок. В каждом калькуляторе очищает `Лист для загрузки вех!B3:V` и копирует туда строки выгрузки, у которых колонка G (`Проект`) равна `калькулятор!A1`. Затем сохраняет калькулятор. Сами вехи в калькулятор этот макрос не вставляет.
- **Формулы калькулятора** подтягивают плановые даты из этого листа:
  - `Лист для загрузки вех!A` = `C & " " & H` (наименование и очередь); формула ключа протянута примерно до 66-й строки;
  - `калькулятор!B` = `E & " " & F`;
  - `G` = `IFERROR(DATEVALUE(VLOOKUP(B; 'Лист для загрузки вех'!A:L; 12; 0)); "")`.
- Что из этого следует:
  - дата на листе должна быть **текстом**: число Excel даёт ошибку `DATEVALUE` и пустую ячейку;
  - при двух строках с одним наименованием и очередью берётся первая;
  - строки ниже конца формулы ключа не находятся;
  - факт (`H`) в калькуляторах вводится вручную;
  - у выплаченных вех формулы часто заменены значениями.
- **«Вставить вехи в новый калькулятор»** вставляет сами вехи в строки калькулятора по данным его листа. Правила отбора — `NEW_CALC` §4.
