# Загрузчик расстановок

Дополнение к комплекту `sov-bonus-kit`. Положить в `docs/RASST.md`. Что добавить в `CLAUDE.md` и `docs/DECISIONS.md` — в разделе 12.

Расстановка — квартальный отчёт руководителей о том, кто на каких проектах работал. Пока 1С УП ШР не подключена, это главный источник назначений и дат прихода и ухода, а для РП и ЗРП ещё и загрузки. Загрузчик расстановок — ещё один тип файла в общем порядке загрузки (ТЗ, раздел 5): распознать, проверить, сопоставить, показать предпросмотр, применить с журналом, откатить. Отличие от других загрузчиков в том, что у расстановки много спорных мест. Поэтому главный результат загрузчика — не только изменения назначений, но и **список разбора с вопросами**.

Правила ниже выведены из ручной сверки расстановок 3 кв. 2026 по КУПК (РП, ЗРП) и ДРП (ОРП 1–3) с действующими калькуляторами. Все примеры условные.

---

## 1. Ограничения

Действуют все жёсткие правила `CLAUDE.md`. Дополнительно:

- Агент разрабатывает и тестирует загрузчик **только на условных расстановках** из `samples/rasst/` (раздел 10). Реальные расстановки содержат ФИО, и их открывает только пользователь в запущенном приложении.
- Загрузчик ничего не пишет в исходные файлы и не открывает `.xlsm`.
- Строки, которые не удалось сопоставить, в реестр не попадают, только в список разбора (ТЗ 5, п. 2).

## 2. Входные макеты и распознавание

Тип определяется по шапке. Лист квартала выбирается по названию (`3 квартал`, `3Q2026`), а если таких листов несколько или ни одного — пользователь выбирает лист в предпросмотре. Листы прошлых кварталов читаются только как контекст: по ним видно, когда человек пришёл или ушёл, если в текущем листе это не написано.

| Тип | Признак шапки | Столбцы | Особенности |
| --- | --- | --- | --- |
| `RASST_KUPK_ZRP` | `ЗРП / руководитель`, `Период`, `Проект (вес)`, `Итого`, `СОВ` | A: `Фамилия Имя` + перенос строки + `РП: …` или `ДП: …`; B: период `ДД.ММ.ГГГГ - ДД.ММ.ГГГГ`; C: `Проект (очередь) (вес)`; D: x; E: СОВ, % | Ячейки объединены по вертикали. У одного человека может быть несколько периодов |
| `RASST_KUPK_RP` | блоки `РП: … \| ДП: …`, под ними `Период`, `Проект (вес)`, `Итого`, `Класс`, `Этап`, `Размер`, `Очереди`, `Дополнительные объекты`, `СОВ / статус`, `Комментарий` | как в шапке | `СОВ / статус` вида `144% / Выше нормы`. В комментарии пишут, что изменилось: `Δ веса`, «изменен этап проекта» |
| `RASST_ORP_A` | `ФИО`, `Проекты в работе`, `Очереди в работе…`, `Дата начала…`, `Дата ухода…` (с колонки A) | A–E | ФИО повторяется в каждой строке. Очередь: `все очереди`, `4 очередь` или пусто. Уход: дата или `до окончания этапа` |
| `RASST_ORP_B` | `ФИО`, `Проекты в работе`, `Этап проекта`, `% участия`, `Итого %`, `Дата начала…`, `Дата ухода…`, `Комментарий` (с колонки B) | B ФИО, C проект, D очередь, E этап, F %, G итого, H начало, I уход, J комментарий | `-` означает пусто. В «Итого» бывает `#REF!`. В ФИО бывают пометки `(РПП)`, `(ДРП)` и вторая фамилия в скобках |
| `RASST_ORP_C` | `ФИО`, `Проекты в работе`, `Очереди в работе…`, `Дата начала…`, `Дата ухода…` (с колонки B, в A номер) | A №, B ФИО, C проект, D очереди, E начало, F уход | ФИО и номер объединены по вертикали |

Объединённые ячейки разворачивать: значение верхней ячейки диапазона действует на все его строки.

## 3. Единый формат: строка расстановки

Каждая строка отчёта превращается в запись промежуточной таблицы `rasst_line`. Это staging-таблица, а не часть реестра: её строки только объясняют предлагаемые изменения.

| Поле | Тип | Что |
| --- | --- | --- |
| `upload_id` | int | загрузка (таблица `upload`) |
| `source_ref` | str | лист и ячейка: `ЗРП!C12` |
| `unit` | str | `КУПК-РП`, `КУПК-ЗРП`, `ДРП-ОРП1`… — блок и отчёт, задаётся при загрузке |
| `quarter` | str | `2026-Q3` |
| `order` | int | порядок строки в отчёте. По нему же выводятся вопросы |
| `person_raw` | str | как в отчёте |
| `tab_no` | str / null | после сопоставления (п. 4.1) |
| `person_match` | enum | `confirmed`, `suggested`, `ambiguous`, `new` |
| `manager_raw` | str / null | РП или ДП из шапки блока |
| `project_raw`, `project_code` | str / null | как в отчёте и после сопоставления |
| `queues` | json | список очередей реестра или `"ALL"` (очередь не указана или «все очереди») |
| `stage_reported` | int / null | этап из отчёта, **только для сравнения** |
| `weight` | float / null | вес проекта (КУПК) или % участия (ОРП-Б) |
| `x_total`, `sov_total` | float / null | КУПК: сумма весов и СОВ периода долями (`1.38`, `1.76`) |
| `class`, `size`, `is_queue`, `extra_objects` | | КУПК-РП: из колонок отчёта |
| `period_from`, `period_to` | date | период внутри квартала. Если не задан, весь квартал |
| `join_date`, `leave_date` | date / null | `до окончания этапа`, `-` и пусто дают null |
| `comment` | str / null | |
| `flags` | json | `REF_ERROR`, `DATE_SUSPECT`, `PLACEHOLDER_PROJECT`, `STAGE_LABEL_OUTDATED` |

Из `rasst_line` строится **ожидаемая занятость**: для каждого `tab_no` и каждого дня квартала — набор пар (проект, очередь). С ней сравнивается **фактическая занятость** по назначениям реестра (раздел 6).

## 4. Сопоставление

ТЗ (раздел 4): «по ФИО и названию ничего не связывается». В расстановках нет табельных номеров и кодов проектов, поэтому нужны справочники соответствий. Пользователь подтверждает их в интерфейсе, а записываются они через `manual_decision` с основанием.

### 4.1. Сотрудники: `person_alias (unit, person_raw → tab_no)`

> С 22.10.2026 (D-101) табельного номера нет: сотрудник — `person_id`, сопоставление — общая функция по ФИО (`loaders/persons.py`) и общий справочник `person_alias`; «нужны таб. номер» ниже читать как «нужны ФИО, подразделение, должность».

- Перед сравнением убрать пометки `(РПП)`, `(ДРП)`, `(БРП)`. Вторую фамилию в скобках пробовать как альтернативную.
- Совпали фамилия и имя с ровно одним сотрудником в `employee`: статус `suggested`, первый раз подтверждает пользователь, дальше `confirmed`.
- Совпала фамилия при другом имени: статус `ambiguous`, это вопрос «новый человек или опечатка». Связывать автоматически нельзя.
- Сотрудника нет в `employee`: статус `new`. Нужны таб. номер, полное ФИО, должность.

### 4.2. Проекты и очереди: `project_alias`, `queue_alias`

- Из названия убрать вес `(0,54)`, код очереди `(1)`, `(1.1)`, `(1,2,3)` и хвосты вида `1,2 оч`. Привести к одному виду `ё/е`, `№ 1/№1`, запятые и пробелы.
- Синонимы, встречавшиеся на практике: опечатка (`Тестоская → Тестовская`), `е/ё` и запятая (`Пробневский 11` и `Пробнёвский, 11` → `Пробнёвский 11`), арабские и римские цифры (`Образец 19 → Образец XIX`), пробел после `№` (`Условный № 1 → Условный №1`), другая форма названия (`Тестовая набережная → Тестовский`). Встречаются и пары совсем разных названий (условно `Старое имя → Новое имя`): их связывать только после подтверждения. Названия условные, правила нормализации те же, что для реальных.
- Очередь в реестре — это **калькулятор**. Один калькулятор может вести две очереди. Тогда это одна очередь реестра с двумя кодами из отчёта. Делитель загрузки считает калькуляторы, а не очереди из отчёта (п. 5.4).
- Код очереди из отчёта переводится в очередь реестра через `queue_alias (project_code, code_raw → queue)`. Порядковый номер не всегда совпадает с номером в названии очереди. Слово «Этап» в названии очереди этапом проекта не является.
- Проект не нашёлся: вопрос. Условные названия вида «Проект 6» бывают рабочими названиями. Не угадывать.

### 4.3. Даты

Даты принимаются как дата или как текст `ДД.ММ.ГГГГ`. Даты вне квартала служат контекстом. Если год не совпадает с реестром или дата расходится на 1–3 дня, ставится флаг `DATE_SUSPECT`. Если это не влияет на квартал, проблема получает низкий приоритет.

## 5. Правила: из расстановки в назначения

### 5.1. Что по факту, а что по плану

1. **Приход, уход и смена загрузки — по факту**, то есть по датам и периодам отчёта.
2. **Этап и его границы — по плану.** Граница этапа для сотрудника — плановая дата ключевой вехи, а если у него есть индивидуальный срок по ней (`individual_date`), то этот срок. Следующий этап начинается на следующий день.
3. Фактическое досрочное или позднее закрытие этапа границы назначений **не** сдвигает: его учитывает К срока. Иначе получится двойной учёт.
4. Конец квартала никогда не используется как дата окончания назначения.
5. Этап, указанный в отчёте, часто устаревший (пишут «3 этап», когда по плану идёт 4-й). Он не переносится, а только помечается флагом `STAGE_LABEL_OUTDATED`.

### 5.2. Какие изменения предлагает загрузчик

| Случай | Изменение |
| --- | --- |
| Пришёл на проект в квартале | новое назначение: `date_from = join_date`, этап по дате прихода |
| Пришёл до начала этапа, а в реестре только назначение на следующий этап | **два назначения**: этап N−1 с даты прихода до своей границы, этап N с границы + 1 и `from_prev_stage = true` |
| Этап закончился внутри квартала, человек остаётся («до окончания этапа», ухода нет) | новое назначение на этап N+1 с границы + 1, `from_prev_stage = true`. **Только если этап N+1 есть в таблице `stage`**, иначе вопрос |
| Ушёл или перевёлся | `date_to = leave_date` (последний рабочий день), `end_reason` |
| Перешёл на другой проект | старое закрыть датой ухода, новое открыть со следующего дня |
| В квартале поменялась загрузка (КУПК) | новая версия набора проектов РП или ЗРП с датой периода (п. 5.4) |

После даты ухода ПБ считается до планового окончания этапа (`CALC_RULES` §2, §11). Это правильно и ошибкой не считается.

### 5.3. Охват

- Предлагается только то, что есть в расстановке текущего квартала. Назначения на проекты, которых нет в отчёте, загрузчик не создаёт.
- Живые назначения людей, которых нет ни в одной расстановке блока, загрузчик не закрывает сам. Это вопрос `RASST_ACTIVE_NOT_IN_REPORTS`.

### 5.4. Загрузка

- **РП (КУПК).** Отчёт РП содержит класс, этап, размер, признак очереди, доп. объекты и вес. Это прямой источник для `rp_project_set`. Загрузчик предлагает версию набора с датой периода, а загрузку считает адаптер по нормированию (`CALC_RULES` §2). Значение `x` и СОВ из отчёта используются как сверка (`RASST_LOAD_MISMATCH`).
- **ЗРП (КУПК).** Отчёт ЗРП содержит веса проектов и СОВ. По расстановке 3 кв. 2026 порог y для ЗРП равен **1,0**: в отчёте ЗРП `СОВ = (x − 1) × 2 + 1` при x > 1, иначе 100%. Так сходятся 17 строк из 18, одна отличается на 0,01 из-за округления. Это ответ на открытый вопрос ТЗ и на толкование **И-1** (раздел 12).
- **Делитель (КУПК, практика расстановки 3 кв. 2026).** СОВ делится на число **проектов**: очереди одного проекта считаются одним проектом. Доля проекта затем делится на число его **калькуляторов**, на которых работает человек. Объект без вех (например, земельные активы) входит в x, но в делитель как проект не идёт.
  - Пример: СОВ 249%, проекты А (1 калькулятор), Б (3 калькулятора), В (1 калькулятор). Получается 83%, 27,67% × 3 и 83%.
  - Буквальное чтение `CALC_RULES` §2 («÷ число проектов и очередей») дало бы 249% ÷ 5 = 49,8% на каждую строку. Это расхождение нужно записать в журнал решений (раздел 12).
- **Остальные (ДРП, МП, РУПК и др.).** Загрузка берётся из таблицы СОВ по должности и этапу, автоматически. Проценты из расстановки (ОРП-Б) только сверяются и в реестр не переносятся. Делить на очереди вручную не нужно: деление и доведение до 100% делает правило `CALC_RULES` §2.
- Загрузка больше 100% (105%, 145%) допустима, движок не должен её резать.

## 6. Сравнение: ожидаемая и фактическая занятость

1. Из назначений реестра собрать фактическую занятость на каждый день квартала. Назначения после даты ухода не учитывать, хотя ПБ по ним продолжается.
2. Сравнить с ожидаемой из раздела 3 по каждому `tab_no` и дню.
3. Расхождения сжать в отрезки: «нет в реестре: проект, очередь, 06.08–30.09» и «лишнее в реестре: проект, 01.07–31.08».
4. Отдельно применить проверки раздела 7, которые ищут причину расхождения и предлагают конкретное изменение.

## 7. Проверки: коды проблем

Это дополнение к `CALC_RULES` §12.2. Формат прежний: `{code, tab_no, milestone?, blocking, message}`, плюс `source_ref`, `order`, `question` (текст вопроса) и `proposal` (предлагаемое изменение, если оно есть). «Блокирует» значит, что строку нельзя применить, пока проблема не разобрана.

| Код | Блокирует | Что обнаружено | Как обнаружить | Вопрос или предложение |
| --- | --- | --- | --- | --- |
| `RASST_PERSON_UNMATCHED` | да | человек не сопоставлен | статус `new` | нужны таб. номер, ФИО, должность |
| `RASST_PERSON_AMBIGUOUS` | да | фамилия та же, имя другое, или несколько кандидатов | статус `ambiguous` | «новый человек или опечатка?» |
| `RASST_PROJECT_UNMATCHED` | да | проект или очередь не найдены | п. 4.2 | какой это проект или калькулятор |
| `RASST_MISSING_ASSIGNMENT` | нет | по отчёту работает, в реестре нет | раздел 6 | предложение по п. 5.2 |
| `RASST_EXTRA_ASSIGNMENT` | нет | в реестре есть, по отчёту нет | раздел 6 | нужна ли дата ухода |
| `RASST_JOINED_BEFORE_STAGE` | нет | пришёл до начала этапа N, назначение только на N | `date_from` раньше границы этапа N, назначения на N−1 нет | два назначения. Перекрытие в 1–3 дня — только вопрос |
| `RASST_NEXT_STAGE_MISSING` | нет | этап закончился в квартале, следующего нет | граница этапа внутри квартала, человек остаётся | предложить N+1, если он есть в `stage`, иначе «есть ли калькулятор и какая плановая дата» |
| `RASST_NONSTANDARD_TERM` | нет | у человека своя дата окончания этапа | дата окончания отличается от самой частой по (проект, очередь, этап), а `individual_date` нет | «индивидуальный срок или опечатка?» |
| `RASST_LEAVE_NOT_IN_REGISTRY` | нет | уход есть в отчёте, но не в реестре, или даты не совпадают | `leave_date` в квартале | закрыть назначение этой датой |
| `RASST_ACTIVE_NOT_IN_REPORTS` | нет | живое назначение, а человека нет ни в одной расстановке блока | фактическая занятость есть, ожидаемой нет | нужна ли дата ухода |
| `RASST_CONFLICT_BETWEEN_REPORTS` | да | человек в двух отчётах с разной загрузкой | один `tab_no` в нескольких `unit`, проекты не совпадают | ушёл со старых проектов или работает на всех |
| `RASST_CROSS_UNIT` | нет | человек в расстановке одного блока, а назначения в другом | разные `unit` в отчёте и в назначениях | переход между блоками, с какой даты |
| `RASST_QUEUES_DIFFER` | нет, низкий приоритет | очереди в отчёте и в реестре разные | конкретная очередь против другого набора, или `ALL` против неполного | списки с обеих сторон. Отчёты часто устаревшие, по умолчанию прав реестр |
| `RASST_LOAD_MISMATCH` | нет | x или СОВ отчёта не сходится с расчётом по набору проектов | п. 5.4 | показать оба значения |
| `RASST_REPORT_ERROR` | нет | ошибка в самом отчёте | `#REF!`, «Итого» не равно сумме, `DATE_SUSPECT` | для информации |
| `RASST_STAGE_LABEL_OUTDATED` | нет | этап в отчёте не совпадает с плановым | п. 5.1, пункт 5 | для информации, ничего не делать |

Проблемы с решением в журнале (раздел 8) получают уровень «принято» и не повторяются как вопрос.

## 8. Решения: `manual_decision`

Каждое решение записывается с основанием (`basis`) и автором. Типы для расстановок:

| kind | Что значит | Пример `payload_json` |
| --- | --- | --- |
| `person_alias` | имя из отчёта соответствует таб. номеру | `{"unit":"ДРП-ОРП2","person_raw":"Тестова Анна","tab_no":"T0041"}` |
| `project_alias`, `queue_alias` | синоним проекта или очереди | `{"from":"Тестовая набережная","to":"TP-07"}` |
| `individual_term` | индивидуальный срок, не ошибка. Создаёт `individual_date` по ключевой вехе этапа | `{"tab_no":"T0041","project_code":"TP-07","stage":5,"milestone_code":"TP-07-5-K","date":"2027-05-30"}` |
| `leave_as_is` | этап закончился по стандартному сроку, новых назначений не нужно | `{"tab_no":"T0042","project_code":"TP-03"}` |
| `ignore` | не трогать (короткое перекрытие, особый случай) | `{"tab_no":"T0043","codes":["RASST_JOINED_BEFORE_STAGE"]}` |
| `queues_ok` | человек на всех очередях, отчёт устарел | `{"tab_no":"T0044","project_code":"TP-07"}` |
| `works_on_all` | человек в двух отчётах работает на всех проектах | `{"tab_no":"T0045"}` |
| `test_assignment` | согласованное тестовое назначение | `{"tab_no":"T0046","project_code":"TP-09","from":"2026-08-06","to":"2026-09-30"}` |

Решения по сопоставлению и индивидуальным срокам действуют, пока их не отменят. Решения `leave_as_is`, `ignore`, `queues_ok`, `works_on_all` действуют в пределах квартала, если пользователь не отметил «постоянно». Квартал и признак хранятся в `payload_json`: `"quarter":"2026-Q3"`, `"permanent":false`.

## 9. Интерфейс

Экран **«Расстановки»** в панели Группы СОВ, рядом с «Загрузкой» (`docs/UI.md` §2):

1. Загрузить файлы расстановок квартала. Для каждого показывается распознанный тип и выбранный лист.
2. Сопоставление: таблица несопоставленных имён, проектов и очередей с кнопками «подтвердить» и «выбрать».
3. По каждому отчёту, **в порядке строк отчёта**: строка, статус («сходится» / «изменение» / «вопрос»), предлагаемое изменение.
4. Блок «Поправить»: предлагаемые изменения назначений, применяются общим механизмом загрузки (предпросмотр, «Применить», журнал, откат).
5. Блок «Вопросы» с кнопками решений из раздела 8 и кнопкой **«Текст для коллеги»**:
   - вопросы по отчётам в порядке строк;
   - по одному-два обычных предложения на человека;
   - без шаблона «Фамилия: …»;
   - с номерами и датами в формате `ДД.ММ.ГГГГ`.
6. Строка «Принято как есть» со ссылками на решения.

Повторная загрузка той же или исправленной расстановки показывает **только разницу** с прошлой загрузкой и оставшиеся вопросы.

Из реестра после применения работают уже существующие экраны: «Сотрудники» (кто на каком проекте, загрузка, индивидуальные сроки, просрочки по вехам), «Проекты» (команда этапа) и выписка по проекту и этапу в виде листа «калькулятор» (`DATA_FORMATS` §6).

## 10. Тесты

- Генератор `tools/make_rasst_samples.py` собирает условные расстановки всех пяти типов (`samples/rasst/*.xlsx`) из сценариев `tests/rasst/scenarios.json`. Файлы должны повторять реальную вёрстку: объединённые ячейки, перенос строки с `РП: …`, вес `(0,54)`, `-`, `до окончания этапа`, `#REF!`, листы прошлых кварталов.
- Ожидаемый результат по каждому сценарию лежит в `tests/rasst/expected/<ID>.json`: множество кодов проблем и список предлагаемых изменений.

| ID | Что проверяет |
| --- | --- |
| R01 | все пять макетов распознаются, объединённые ячейки развёрнуты |
| R02 | пометки в ФИО, вторая фамилия, `ambiguous` при другом имени, `new` |
| R03 | синонимы проектов, вес и код очереди в названии, калькулятор на две очереди |
| R04 | приход в квартале, новое назначение |
| R05 | приход за 5 недель до начала этапа: два назначения. Приход за 2 дня: только вопрос |
| R06 | этап закончился в квартале: N+1 предложен, если он есть в `stage`, иначе вопрос |
| R07 | индивидуальный срок: следующий этап начинается после него. Без `individual_date` — `RASST_NONSTANDARD_TERM` |
| R08 | уход и переход на другой проект в один день |
| R09 | человек в двух отчётах: `RASST_CONFLICT_BETWEEN_REPORTS` |
| R10 | живое назначение вне отчётов |
| R11 | отчёт с устаревшими этапом и очередями: только флаги, без изменений |

## 11. Опыт 3 кв. 2026: что считать нормой

- Отчёты часто устаревшие. Этап, список очередей и даже проекты, с которых человек уже ушёл, могут остаться с прошлого квартала. Это вопрос, а не автоматическая правка, и после подтверждения прав реестр.
- Индивидуальные сроки по одному этапу бывают у части команды (у одних 08.09, у остальных 12.08). Следующий этап у каждого начинается после его собственной даты.
- Если этап закончился по стандартному сроку, а калькулятора следующего этапа нет, назначение не продлевается (`leave_as_is`).
- Короткое перекрытие этапов в 1–3 дня могут решить не исправлять (`ignore`).
- Условные названия проектов бывают рабочими. Тестовые назначения бывают согласованными (`test_assignment`).
- Новый человек часто приходит в отчёте под коротким именем или с другим именем при той же фамилии.
- Сотрудник может перейти между блоками (из ДРП в КУПК) и остаться без даты ухода в старом блоке.

## Приложение А. Параллельный расчёт и перенос листа «Данные»

Нужно на время параллельного расчёта рядом с калькуляторами (ТЗ, раздел 12, п. 5), чтобы объяснять расхождения с «Историей» макрокниги. Агент работает только с условной выгрузкой листа в `.xlsx` или `.csv`, `.xlsm` не открывает.

Как макрос «Обновить историю» читает лист «Данные» (проверено: эмуляция совпала со свежей «Историей» обеих книг на каждый день квартала):

- Ключ задачи — `ФИО|Проект|Очередь` **без trim**. Лишний пробел в ФИО даёт второго сотрудника. Этап в ключ не входит.
- Строка пропускается, если дата старта не дата или дата старта позже даты ухода. Нечисловой процент считается нулём. Число больше 1 делится на 100: 105% превращается в 1,05%, это ошибка макроса.
- При одинаковой дате старта нижняя строка перезаписывает верхнюю. На этом держатся заглушки при создании калькулятора: РП 100%, МП 50%.
- Сегмент длится до следующей даты старта, последний — до **максимальной** даты окончания по ключу. Ключ без единой даты окончания пропускается целиком.
- После даты ухода коэффициент замораживается, строка выводится до конца сегмента.
- БПП и ОИ: коэффициент = процент. Остальные, с 01.07.2025: процент делится на число очередей проекта в периоде, сумма меньше или равная 1 растягивается до 1.
- Новые строки «Истории» пишутся поверх старых, а **хвост старой «Истории» остаётся** ниже. Граница видна по `sortState ref` в XML листа. «Расчёт ПБ» и загрузка в калькуляторы берут хвост тоже, поэтому его удаляют до них.

При переносе «Данных» в реестр каждая строка становится назначением или версией загрузки. Перед этим проверить: пробелы в ФИО, проценты больше 1, ключи без даты окончания, неперекрытые заглушки и названия очередей, не совпадающие с калькуляторами.
